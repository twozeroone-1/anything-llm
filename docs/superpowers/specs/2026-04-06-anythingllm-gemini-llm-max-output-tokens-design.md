# AnythingLLM Gemini LLM Max Output Tokens Design

## Summary

Add a Gemini-specific `max output tokens` setting under the instance-level `AI Provider > LLM > Gemini` configuration so administrators can cap the length of Gemini-generated answers.

This setting applies to the final LLM response only:

- normal workspace chat replies
- RAG-backed final answers after retrieval/context injection

This setting does not change:

- embedding requests
- vector search or retrieval breadth
- document chunking
- agent/Aibitat execution

## Scope

In scope:

- Add a new Gemini LLM setting in the existing LLM preference UI.
- Persist the setting through the current system settings + env update flow.
- Apply the setting to the general Gemini chat provider used by workspace chat and RAG final response generation.
- Apply the same cap to both non-stream and stream Gemini chat responses.
- Surface the saved value back into the settings UI.
- Add regression tests for settings persistence and Gemini provider payload generation.

Out of scope:

- Changing embedding or retrieval token behavior.
- Adding a provider-agnostic global max output token setting.
- Applying the cap to agent/Aibitat Gemini executions.
- Reworking RAG retrieval size, reranking, or context window filling.
- Refactoring unrelated LLM providers.

## User Experience

### Chosen Direction

Use a provider-specific Gemini setting inside the existing Gemini LLM configuration panel.

Rationale:

- It matches user expectation because Gemini is selected in `AI Provider > LLM`.
- It naturally affects the final answer generator for both plain chat and RAG replies.
- It avoids introducing a second RAG-only control that would be harder to reason about.

### Setting Behavior

The Gemini settings panel will expose one new numeric field:

- `Gemini max output tokens`

Behavior rules:

- Blank means "use Gemini/provider default".
- A positive integer means "cap the final generated answer at this many output tokens".
- Invalid values such as `0`, negatives, or non-numeric strings are rejected by the existing settings save path.
- The setting is instance-wide, not workspace-specific.

### Expected Result

If the admin sets Gemini max output tokens to a small value, then:

- regular Gemini chat answers should become shorter
- RAG final answers should also become shorter
- retrieval still runs as before, but the final answer generation stops earlier

## Technical Design

### Current Flow

AnythingLLM RAG and non-RAG chat flows both assemble a prompt and then call the currently selected LLM provider through `getLLMProvider()`.

Relevant paths:

- `server/utils/chats/apiChatHandler.js`
- `server/utils/chats/stream.js`
- `server/utils/chats/openaiCompatible.js`
- `server/utils/chats/embed.js`

For Gemini, the final answer is generated by:

- `server/utils/AiProviders/gemini/index.js`

That means a Gemini LLM output cap belongs in the Gemini LLM provider layer, not in retrieval or embedding code.

### Official Documentation Constraint

Google's official Gemini native API documents `maxOutputTokens` on `generateContent`.

Official references:

- `generateContent` API: <https://ai.google.dev/api/generate-content>
- Gemini partner integration guidance: <https://ai.google.dev/gemini-api/docs/partner-integration>
- OpenAI compatibility guide: <https://ai.google.dev/gemini-api/docs/openai>

Important constraint:

- The current AnythingLLM Gemini chat provider does not use the native Gemini SDK or native `generateContent`.
- It uses Google's OpenAI-compatible endpoint at `https://generativelanguage.googleapis.com/v1beta/openai/`.
- Google's official OpenAI compatibility guide does not clearly document a Gemini-specific output-token parameter the same way the native API documents `maxOutputTokens`.

Because of that, the implementation should treat the request-field choice as an implementation inference from the OpenAI Chat Completions surface, not as a direct Google-native API contract.

### Chosen Implementation Strategy

Keep the current Gemini chat transport for now and add a provider-level output cap in the existing Gemini LLM provider.

Design intent:

- Add the configuration surface first.
- Inject the output cap into Gemini chat-completion requests in one place.
- Verify with a live smoke test that the compatibility endpoint actually honors the cap for the configured Gemini models.

Why this is preferred right now:

- It delivers the requested admin control with a much narrower change set.
- It avoids a larger Gemini provider migration unless the compatibility endpoint proves unreliable.
- It keeps the setting scoped to final text generation, which is the user requirement.

### Fallback Rule

If the live smoke test shows that the compatibility endpoint ignores or rejects the cap, do not silently ship partial behavior.

Instead:

- stop at the failed validation
- document the observed behavior
- open a follow-up design to migrate only the general Gemini chat provider to the native Gemini API so the cap can be implemented with native `maxOutputTokens`

Primary configuration surface:

- `frontend/src/components/LLMSelection/GeminiLLMOptions/index.jsx`
- `server/models/systemSettings.js`
- `server/utils/helpers/updateENV.js`

- `server/utils/AiProviders/gemini/index.js`

Likely supporting tests:

- `server/__tests__/utils/helpers/updateENV.gemini.test.js`
- `server/__tests__/utils/AiProviders/gemini/index.test.js`
- `server/__tests__/models/systemSettings.test.js`

## Configuration Shape

UI/system setting key:

- `GeminiLLMMaxOutputTokens`

Environment variable:

- `GEMINI_LLM_MAX_OUTPUT_TOKENS`

Stored semantics:

- unset or empty: no explicit output cap
- positive integer string: explicit cap

## Provider Behavior

### Prompt Construction

Prompt construction remains unchanged.

The current Gemini provider already builds:

- system prompt
- appended context texts for RAG
- formatted chat history
- current user message

The new setting only affects the response-generation step after that prompt is already built.

### Request Construction

The Gemini provider should build a single request options object for both:

- `getChatCompletion`
- `streamGetChatCompletion`

That request object should:

- always include existing model, messages, and temperature fields
- include an output-token limit only when `GEMINI_LLM_MAX_OUTPUT_TOKENS` is set

Because the current transport is OpenAI-compatible chat completions, the request field should be treated as an OpenAI-compatible request option rather than a native Gemini `config.maxOutputTokens` field.

The exact field name is an implementation choice that must be validated by a live smoke test before the feature is considered complete.

### RAG Impact

No RAG retrieval code needs custom branching.

Once the Gemini provider respects the output cap:

- standard workspace chat responses will be capped
- RAG final answers will also be capped

This works because both paths ultimately call the same general Gemini LLM provider.

## Error Handling

- Saving an invalid numeric value should fail through the normal settings validation path.
- Leaving the field blank should remove the explicit cap and fall back to current provider defaults.
- If the Gemini compatibility endpoint rejects the output cap option, the failure should be visible during implementation smoke testing and must block completion of the feature.
- The feature must not alter existing Gemini API key fallback behavior.

## Testing Strategy

Minimum automated coverage:

1. `updateENV` accepts a valid Gemini max output token value.
2. `updateENV` rejects invalid values such as `0`.
3. `SystemSettings.currentSettings()` exposes the saved value back to the UI.
4. Gemini non-stream requests include the cap when configured.
5. Gemini stream requests include the cap when configured.
6. Gemini requests omit the cap when unset.
7. Existing Gemini key fallback tests still pass.

Required manual verification:

1. Run AnythingLLM locally or in a test container with Gemini selected as the LLM provider.
2. Set a very small Gemini max output token value.
3. Ask a deliberately long-answer question in normal chat.
4. Ask a RAG-backed question in query mode.
5. Confirm both final replies are noticeably shorter.
6. If not, treat the compatibility route as unverified and stop for follow-up design.

## Risks

- Google's OpenAI compatibility documentation does not clearly document the same token-cap option that native Gemini documents, so runtime validation is required.
- Some Gemini preview models may behave inconsistently with completion limits.
- A very small cap can produce answers that look truncated or incomplete; that is expected behavior and not a bug.
- If the UI defaults this value too aggressively, users may unknowingly clip normal chat answers, so blank/default-off is safer than a hardcoded number.

## Implementation Notes

- Keep the first version provider-specific and minimal.
- Do not add embedding-side limits as part of this work.
- Do not apply the cap to agent/Aibitat Gemini until there is a separate requirement.
- Prefer reusing the existing Gemini provider test file instead of introducing broad integration test scaffolding unless required.
